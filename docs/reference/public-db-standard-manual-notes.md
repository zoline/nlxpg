# 공공데이터베이스 표준화 관리 매뉴얼: nlxpg 연관 항목

- 원문: 「공공데이터베이스 표준화 관리 매뉴얼」 (행정안전부, 2026.4, 281쪽). 로컬 사본 `docs/reference/1._공공데이터베이스_표준화_관리_매뉴얼_2026_04.pdf`는 이용 조건 표시가 없어 저장소로 배포하지 않는다(`.gitignore`). 원문은 한국지능정보사회진흥원(NIA)·공공데이터포털 배포본을 받는다. 지침 고시: [행정안전부 고시 제2025-19호 안내](https://www.mois.go.kr/frt/bbs/type001/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000016&nttId=115982)
- 쪽 번호는 매뉴얼에 인쇄된 쪽 번호다. PDF 뷰어의 쪽 번호는 여기에 9를 더하면 된다.
- 정리일: 2026-09-30

## 요약

이 매뉴얼은 nlxpg의 두 가지 미정 사항에 구체적인 기준을 준다.

1. **명명 표준** (docs/adr/README.md 결정 대기 항목): 공통표준은 용어·단어·도메인의 생성 규칙과 영문약어 규칙을 정해 둔다. 이 규칙을 채택하면 논리명은 표준용어명, 물리명은 표준용어 영문약어명이 되고, 데이터 타입과 길이는 표준도메인에서 결정된다.
2. **산출물 형식**: 「공공기관의 데이터베이스 표준화 지침」 별표 제2호가 산출물 7종의 필수 관리항목을 정한다. 현재 nlxpg의 DDL, ERD, 설명서만으로는 이 항목을 다 채울 수 없고, 중간 표현(IR)에 필드를 더해야 한다.

공통표준 용어·단어·도메인의 **전체 목록은 매뉴얼에 없다.** 목록은 공공데이터포털과 품질·표준관리 통합시스템(std.sharedata.go.kr)에 등록되어 있고, 행정표준코드는 code.go.kr에 있다. 구현하려면 이 목록을 따로 받아야 한다.

## 1. 표준 체계 (Ⅰ.4.2, 7~8쪽; Ⅳ.1, 97~101쪽)

| 구성요소 | 내용 | nlxpg에서의 쓰임 |
| --- | --- | --- |
| 표준단어 | 업무용어 기반 최소 단위의 명사형 단어. 한글명, 영문명, 영문약어명, 형식단어 여부, 도메인분류명, 이음동의어, 금칙어 | 추출된 속성명을 단어로 분할하고 대표단어로 정규화 |
| 표준도메인 | 도메인그룹 > 분류 > 도메인명(`분류명+타입+길이`, 예: 연월일C8). 타입, 길이, 소수점, 저장·표현형식, 단위, 허용값 | 데이터 타입·길이 결정 |
| 표준용어 | 표준단어의 조합 + 표준도메인. 마지막 단어는 형식단어 | 속성 논리명·물리명·타입을 한 번에 결정 |
| 표준코드 | 한글·영문코드명, 타입, 길이, 코드값, 코드값의미. 행정표준코드 우선 | 코드성 속성의 값 목록 |

표준 적용 범위는 **공통표준 → 기관표준 → DB표준** 순서로 준용한다(8쪽). nlxpg가 새로 만드는 스키마는 "DB표준"에 해당하고, 공통표준에 없는 용어는 DB표준으로 새로 정의해야 한다.

## 2. 명명 규칙 → 5단계 모델링 (Ⅳ.2~3, 102~129쪽)

### 표준용어명 (논리명) — [표 Ⅳ-4], 105~106쪽

| 규칙 | 예시 |
| --- | --- |
| 표준단어의 조합으로만 구성하고, **마지막 단어는 형식단어**여야 한다 | 이메일수신(X) → 이메일수신동의여부(O) |
| 단어는 가급적 6개 이하 | SMS수신동의여부 |
| 복합어가 있으면 복합어를 우선 선택 (영문약어 30자 제약 때문) | 전화번호 > 전화+번호 |
| 띄어쓰기·특수문자 금지 | 거래_일자(X) → 거래일자 |
| 한 용어가 여러 의미를 갖지 않게 | 공사시작및종료일자(X) → 공사시작일자, 공사종료일자 |
| 부서명 사용 금지 | 기획실담당자전화번호(X) |
| 코드성 용어는 반드시 `~코드` | 학력(X) → 학력코드, 신청구분(X) → 신청구분코드 |
| 의미 없는 일련번호 숫자 금지 | 전화번호1(X) → 회사전화번호, 휴대전화번호 |
| '누계', '합계'는 형식단어 앞 | 평가합계점수 |
| 여부 vs 유무: 단건 참·거짓은 여부, 여러 건 중 존재는 유무 | 공개여부(O), 첨부파일유무(O) |

### 영문약어명 (물리명) — 108쪽, [표 Ⅳ-19] 120~121쪽

- 용어 영문약어명 = 단어 영문약어명을 `_`로 연결하고, **최대 30자**(`_` 포함). 예: 계약종료일자 → `CTRT_END_YMD`, 등록일자 → `REG_YMD`
- 단어 영문약어명: 대문자, **최대 6자, 가급적 4자 이내**
  - 첫 글자 외의 모음을 빼고 대표 자음 사용 (Demand → DMND)
  - 연속 자음은 하나 생략 (Success → SCS)
  - 첫 글자가 모음이면 유지 (Action → ACTN)
  - 영문명이 4자 이내면 그대로 (Join → JOIN)
  - 관용 약어 우선 (Month → MM, Error → ERR, Business → BIZ)
  - 한글 발음 표기 금지 (GONGJI(X) → NTC). 행정동 '동', '리' 같은 예외는 허용
  - 약어는 유일해야 한다. 같은 영문명을 쓰는 이음동의어만 예외 (명/이름 → NM)

### 단어 정규화 — [표 Ⅳ-15]~[표 Ⅳ-25], 113~129쪽

- **단어 분할 → 형식단어 도출 → 대표단어 선정**의 3단계 (113쪽). 예: 계약시작일자 → 계약 / 시작 / 일자
- 대표단어 선정 순서: 표준국어대사전 → 기술·산업 표준 → 법령·지침 → 다기관 사용 빈도 → 국립국어원 '다듬은 말'
- **이음동의어**(연도/년도, 구매/구입/매입, 이메일/전자우편)는 대표단어로 통합한다. 영문약어도 대표단어와 같다.
- **금칙어**(화일, 유저, 주민번호, 종업원)는 쓰지 않는다.
- 동음이의어는 원칙적으로 금지하고, 복합어로 구분한다 (수입(Income) vs 수입관세).
- 이음동의어로 볼 수 없는 예(의미 차이가 있음): 고시·공고·공지, 교부·발급, 변경·변동 (124쪽)

**nlxpg 영향:**
- 엔티티 정합(4단계)의 "동의어 사전"을 공통표준단어의 이음동의어·금칙어 목록으로 초기화할 수 있다.
- 현재 [modeling/naming.py](../../nlxpg/modeling/naming.py)는 LLM이 제안한 영어 snake_case를 그대로 쓴다(예: `customer_name`). 공통표준을 채택하면 `CUST_NM` 방식의 약어로 바꿔야 한다.
- PostgreSQL은 따옴표 없는 식별자를 소문자로 바꾸므로, 물리명은 소문자 약어(`cust_nm`)로 두는 편이 현실적이다(결정 필요).

## 3. 표준도메인 → 타입 추론 (Ⅳ.4, 130~147쪽)

형식단어 → 도메인분류 → 도메인명으로 타입이 정해진다. [표 Ⅳ-32]의 주요 도메인:

| 그룹 | 대표 도메인 | 타입 | 비고 |
| --- | --- | --- | --- |
| 금액 | 금액N15 (N13, N17, N18, N22,2), 가격N10/N15, 비용N15, 요금N15 | NUMERIC | |
| 날짜/시간 | 연도C4, 연월C6, **연월일C8**, 월C2, 시분C4, 시분초C6, 연월일시분C12 | CHAR | 저장형식 YYYYMMDD 등, 특수문자 없이 |
| 날짜/시간 | 연월일시분초D 또는 연월일시분초C14 | DATETIME / CHAR(14) | DB 특성에 맞춰 선택 |
| 내용 | 내용V1000 / V2000 / V4000 | VARCHAR | |
| 명칭 | 명V5 ~ 명V300, 주소V200 등, 상세주소V200 | VARCHAR | 아이디·주소도 명칭 그룹 |
| 번호 | 번호C6~C24, 번호V3~V100, 일련번호N10/N22, 주민등록번호C13, 사업자등록번호C10, 법인등록번호C13, 전화번호V11, 우편번호C5, 암호화번호V256 | CHAR / VARCHAR / NUMERIC | 식별번호는 문자형이 기본 |
| 수량 | 수N2~N14, 면적N19,9, 경도N13,10, 위도N12,10, 순서N10 | NUMERIC | |
| 율 | 율N5,2 / N6,2 / N7,2 / N12,6, 비율N12,9 | NUMERIC | |
| 코드 | 여부C1 ('Y'/'N'), 유무C1, 코드C1~C12 | CHAR | |

- **길이는 바이트 기준이고 한글은 2바이트**(EUC-KR 기준)다. 한글 100자를 받는 기관명은 VARCHAR(200) (146쪽)
- 저장형식에는 표현용 특수문자를 넣지 않는다. 등록일자: 2020-01-01(X) → 20200101(O) (109쪽)
- 같은 이름의 용어에 다른 도메인을 지정하지 않는다(데이터 검증 오류 원인, 109쪽)

**nlxpg 영향:**
- 현재 [modeling/types.py](../../nlxpg/modeling/types.py)는 값 예시 `2026-09-30`을 `date`로 추론한다. 공통표준은 연월일을 `CHAR(8)`로 저장한다. 어느 쪽을 따를지 정해야 한다.
- 여부 속성은 `boolean` 대신 `CHAR(1)` + 'Y'/'N'이 표준이다.
- PostgreSQL의 `varchar(n)`은 바이트가 아니라 문자 수다. 공통표준 길이를 그대로 옮기면 한글 기준으로 2배 여유가 생긴다(문제는 없지만 평가 시 타입 일치 판정에 영향).
- 타입 결정의 1순위는 LLM 힌트가 아니라 "마지막 단어(형식단어) → 도메인" 매핑이 되어야 한다.

## 4. 표준코드 (Ⅳ.5, 148~152쪽)

- 코드성 속성은 먼저 **행정표준코드**(code.go.kr)에 있는지 확인하고, 없을 때만 기관·DB 표준코드로 정의한다.
- 관리항목: 관리부서명, 한글코드명, 영문코드명(예: 국가코드/`NTN_CD`), 코드설명, 데이터타입, 데이터길이, 코드값, 코드값의미
- '기타' 코드값은 같은 타입·길이로 부여한다 (예: 'zz', '99')

**nlxpg 영향:** 추출 단계의 `value_examples`에서 코드값 후보를 모아 코드 정의서 초안을 만들 수 있다. 예: 샘플 문서의 "거래처 등급: 일반, 우수, VIP" → 거래처등급코드.

## 5. 모델링 규칙 → 5단계 모델링, 7단계 검증

별표 제2호(264쪽~)와 진단항목 2.1~2.2(35~36쪽)에서 뽑은 규칙:

| 규칙 | 출처 | nlxpg 적용 |
| --- | --- | --- |
| 속성유형: 기본형(업무에서 직접 도출), 설계형(코드처럼 값을 고안), 추출형(다른 속성에서 계산) | 별표 제2호 애트리뷰트정의서 | 추출 스키마에 속성유형 추가. 추출형은 정규화 검사 대상 |
| 필수입력여부: M(필수) / C(조건부필수, 조건은 속성설명에) | 별표 제2호 | 현재 `required: bool`을 3값으로 확장 |
| 식별자: PK, AK(Unique / Not-Unique 구분), FK와 참조 엔터티·속성 | 별표 제2호 | 현재 `is_unique`를 AK로 일반화 |
| 수퍼타입/서브타입 엔터티와 범주 구별 기준 | 별표 제2호 엔터티정의서 | 현재 미지원 |
| 주식별자가 여러 속성이면 "+"로 표기 (고객번호+상품번호+계약일자) | 별표 제2호 | 설명서 출력 형식 |
| 인조식별자가 많은 엔터티, 핵심 엔터티는 "데이터 발생 규칙 정의서" 작성 | 진단항목 2.1, 35쪽 | 대리키를 붙인 엔터티에 발생 규칙 설명 생성 |
| 논리모델 검증: 업무규칙 완전성, 정규화 충족 | 진단항목 2.2, 36쪽 | 사람 검토 체크리스트의 "엔터티 완전성", "정규화"와 대응 |
| 물리모델 검증: 중복 테이블·중복 컬럼 목록으로 중복 설계 필요성 검토 | 진단항목 2.2, 36쪽 | 린트 규칙 후보 |
| 엔터티 설명에 목적, 포함/비포함 데이터, 업무 규칙, **개인정보 포함 여부** | 24쪽, 별표 제2호 | 엔터티 설명 생성 프롬프트 |

## 6. 산출물 7종 → 6단계 산출물 생성 (Ⅲ.2, 23~25쪽; 지침 제9조, 별표 제2호)

지침 제9조는 DB를 설계·구축할 때 아래 산출물을 필수로 정한다. 현재 nlxpg 출력과의 차이:

| 산출물 | 필수 관리항목 (요약) | 현재 nlxpg | 부족한 것 |
| --- | --- | --- | --- |
| 논리데이터모델 다이어그램 | 한글DB명, 설명. 엔터티·속성·관계·식별자 포함 | `erd.mmd` (물리명 기준) | 한글 논리명 기준의 별도 ERD |
| 엔터티정의서 | 한글DB명, 엔터티명(표준용어), 설명(목적, 포함/비포함, 업무규칙, 개인정보 포함), 주식별자, 수퍼타입 | `schema.md` 일부 | 주식별자 "+" 표기, 수퍼타입, 개인정보 포함 표기 |
| 애트리뷰트정의서 | 엔터티명, 속성명(표준용어), 속성유형, 필수입력여부(M/C), 식별자(PK/AK/FK), 참조 엔터티·속성, 속성설명 | `schema.md` 일부 | 속성유형, M/C, AK, 참조 속성 |
| 데이터베이스정의서 | 기관명, 부서명, 관련법령, 한글·영문DB명, 구축일자, DB설명, 업무분류체계(BRM 4단계), DBMS, OS, DB형태 | 없음 | 대부분 사람이 입력할 항목. 템플릿만 생성 |
| 물리데이터모델 다이어그램 | 영문DB명, 설명. 테이블·컬럼·관계·식별자 포함 | `erd.mmd` | 설명·이력 |
| 테이블정의서 | 영문DB명, 테이블 소유자, 한글·영문 테이블명, 테이블 유형(코드/마스터/임시/통계 등), 관련 엔터티명, 설명, 발생주기 | `schema.md` 일부 | 테이블 유형, 발생주기 |
| 컬럼정의서 | 영문테이블명, 한글·영문 컬럼명, 설명, 연관 엔터티·속성명, 타입, 길이, Not Null, PK정보(`PK01`), AK정보(`AK_1-01`), FK정보(`T_CUST.CUST_ID`), 제약조건, **개인정보 여부, 암호화 여부, 공개/비공개 여부** | `schema.md`, DDL | PK 순서, AK, 제약조건, 개인정보·암호화·공개 여부 |

추가로 지침 별표 제1호(261쪽~)는 **데이터 표준사전**(표준용어·단어·도메인·코드 정의서)의 관리항목을 정한다. 공통표준에 없는 용어를 nlxpg가 새로 만들면, 그 용어를 DB표준 후보로 표준사전 형식에 맞춰 함께 출력하는 것이 자연스럽다.

**nlxpg 영향:** IR(`nlxpg/ir.py`)에 필드를 더해야 한다(schema_version 0.2).
- 속성: 속성유형, 필수입력 M/C와 조건, AK 그룹·순서, 도메인명, 허용값, 저장·표현형식, 개인정보·암호화·공개 여부
- 엔터티: 수퍼타입, 테이블 유형, 발생주기, 개인정보 포함 여부
- 스키마: 한글·영문 DB명, 설명

## 7. 비표준 데이터 매핑 → 평가 (Ⅲ.1.3, 14~22쪽)

- 표준 여부 판정에 쓰는 네 항목: **한글 컬럼명, 영문 컬럼명, 데이터 타입, 데이터 길이** ([표 Ⅲ-1], 17쪽)
- 명칭이 같으면 이름으로 판정하고, 다르면 의미로 판정한다.
- 매핑 예시 ([표 Ⅲ-2]): 법정동코드 `LEDCD VARCHAR(5)` → `STDG_CD CHAR(10)`, 등록일자 `REGIST_DE VARCHAR(8)` → `REG_YMD CHAR(8)`

**nlxpg 영향:**
- 이 구조는 ADR-0003의 의미 기반 매칭(생성 스키마 ↔ 정답 스키마)과 같다. 평가 결과를 이 매핑정보 형식으로 내보내면 DBA가 익숙한 형식으로 검토할 수 있다.
- 평가 지표에 **공통표준 준수율**(생성 컬럼 중 공통표준용어와 일치하는 비율)을 추가할 수 있다.
